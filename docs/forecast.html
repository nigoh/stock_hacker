Overnight forecast · 予想 → 答え合わせ → 台帳

予想を出しっぱなしにしない

夜間フォーキャストは、翌営業日の方向・上昇確率・予想レンジを固定ルールで機械的に出し、 翌日の実績終値で必ず採点し、結果を台帳に貯めていく仕組みです。 予想そのものより、予想が採点されて記録に残ることに価値を置いています。 ここで出る数字は将来の断定でも投資助言でもなく、手法を検証可能に保つための測定値です。

Why

なぜ答え合わせなのか

予想の良し悪しは、出したときの説得力ではなく後から記録が決めます。 当たった予想だけを覚え、外した予想を忘れる限り、手法は永遠に評価されません。

そこでこの環境は、まず固定ルールの機械的ベースラインを置きます。 重みも閾値も過去データにフィットさせていないので、「よく当たるように調整された数字」ではありません。 そのぶん出発点として弱いかもしれませんが、当たり外れを同じ条件で積み上げられます。 台帳が貯まって初めて「どのシグナルが効くのか」「確率の付け方は適切か」を議論できます—— これが stocklib/forecast.py の言うデータの醸成です。

設計の順序 重みを過去にフィットさせてから予想を出すのではなく、固定重みで予想を出してから測る。 逆順にするとインサンプル最適化とルックアヘッドの罠に入り、良く見える成績が将来を保証しない。 実測に基づいて重みを見直す場合も、IS/OOS 分割で過剰適合を疑う手続きを必ず通す （backtesting-and-statistics.md）。
Closed loop

閉ループ

01

予想

forecast がユニバース各銘柄の方向・上昇確率・予想レンジを固定ルールで生成する。

02

記録

forecasts/ledger.csv に status=pending の行として upsert される（git 管理対象）。

03

答え合わせ

grade が asof より後の最初の実データ日の終値で採点し、同じ行を graded に更新する。

04

測定

calibration が台帳から方向的中率・Brier・較正表・銘柄別成績を集計する。

05

改善

測定に根拠がある場合だけ手法を直す。少数標本では動かさない。

run は 03（前回予想の答え合わせ）と 01（翌営業日の予想生成）を1コマンドで実行する夜間運用の本体です。 Claude Code からは /overnight で同じループを起動できます。

Model

予想モデルの中身

方向スコア s は、3つの正規化サブスコア（各 −1〜+1）を固定重みで合成しただけのものです。 実装は analysis/stocklib/forecast.py の make_forecast。以下は実装そのままの定義です（C は asof の終値、 σ_d は日次リターンの20日標準偏差）。

s_trend — トレンド（重み 0.40）
終値と25日線の上下、および25/75日線の並びの符号を平均する。 2つの符号の平均なので、取りうる値は {−1, −0.5, 0, +0.5, +1} の5値のみ。
s_mom — モメンタム（重み 0.40）
20営業日リターンを、その期間のボラティリティで割った z 値相当を −1〜+1 に切り詰める。 同じ +5% でも、静かな相場なら大きく、荒れた相場なら小さく評価される。
s_meanrev — 平均回帰（重み 0.20）
RSI(14) が50から離れた分を逆符号で使う。売られすぎなら +、買われすぎなら −。 トレンド追随2項に対する逆張りの重しで、重みは最も軽い。 
# --- 3つのサブスコア（それぞれ -1 〜 +1）---
s_trend = 0.5 * ( sgn(C - SMA25) + sgn(SMA25 - SMA75) )     # ∈ {-1, -0.5, 0, +0.5, +1}
s_mom   = clip( m20 / (σ_d * sqrt(20)), -1, +1 )            # m20 = C / C[-20] - 1
s_rev   = (50 - RSI14) / 50

# --- 合成 → 確率 → 方向ラベル ---
s       = clip( 0.40*s_trend + 0.40*s_mom + 0.20*s_rev, -1, +1 )
p       = 1 / (1 + exp(-1.5 * s))                           # 上昇確率（ロジスティック変換）
direction = up   if p >= 0.55
            down if p <= 0.45
            flat otherwise

# --- 予想値 ---
r̂       = s * σ_d                                          # 予想リターン（1日ぶんの控えめな点推定）
range   = C * (1 + r̂) ± ATR14                              # 予想レンジ（終値ベース）
confidence = |s|                                            # 信頼度＝スコアの絶対値

パラメータはすべて forecast.py の定数です。変更すれば挙動は変わりますが、 変更した時点で、それ以前に貯めた台帳と同じモデルの成績ではなくなる点に注意してください。

定数値意味

SLOW_SMA75長期移動平均（トレンド項）
MOMENTUM_WINDOW20モメンタムの計測日数

重みは固定・未フィット 重み（0.40 / 0.40 / 0.20）・傾き（1.5）・閾値（0.55 / 0.45）はすべて固定値で、 過去データに最適化していません。したがって「バックテストで良かったから選んだ数字」ではなく、 逆に言えば当たるという事前の根拠もありません。 効くかどうかは台帳を貯めて測って初めて分かる、というのがこの設計の前提です。
Grading

採点の仕方

採点は grade_forecast が行います。実績として使うのは asof 日より後の最初の実データ日の終値です（台帳の target_date は 土日だけをスキップした暦日ベースの目安で、祝日は考慮していません。実際に採点に使った日付は actual_date に記録されます）。翌営業日の足がまだ無ければ採点せず pending のまま残します。

項目台帳の列判定
実績リターンactual_return actual_close / asof_close − 1
方向的中dir_hit up は実績リターン > 0、down は < 0、 flat は |実績リターン| ≤ 0.5%（FLAT_BAND）
レンジ的中in_range pred_low ≤ actual_close ≤ pred_high
Brier スコアbrier (prob_up − 1{実績リターン > 0})²。低いほど良い
予想リターン誤差abs_error |実績リターン − pred_return|（集計時は平均して MAE）

方向的中率の集計では flat 予想を分母から除きます（方向を張っていないため）。 一方 Brier とレンジ的中率は flat を含む採点済み全件を母数にします。 なお実績リターンは終値→終値なので、オーバーナイトのギャップを含みます。 寄り付き約定を前提にした評価には別の設計が要ります。

Upsert

同じ日・同じ銘柄は上書き

行のキーは forecast_id = <asof_date>:<code>。同じ営業日に forecast を何度回しても行は重複せず、再生成の意図とみなして上書きされます（採点済みの行でも同一 asof なら上書き）。

Real / Synthetic

合成予想は実データで採点しない

--synthetic で作った予想は data=synthetic と記録され、実データの実績とは採点されません。集計（summarize / calibration_table）も既定で data=real のみを対象にし、実績成績に合成が混ざらないようにしています。

書式の詳細は forecasts/README.md。 個人のウォッチリスト（data/watchlist.csv、git 管理外）を対象にすると、その銘柄コードが git 管理対象の台帳に載る点に注意してください（--ledger で管理外のパスに逃がせます）。

Metrics

評価指標の読み方

理論は knowledge/math/forecast-evaluation-and-calibration.md に置いています。 要点は「的中率だけでは足りない」ことです。

Hit rate

方向的中率

50%は予測力ゼロと同義です。コイン投げの水準を超えているかは標本数が十分になるまで判定できません。また上げ相場では「常に上昇」と言うだけで的中率は上がる（ベースレート問題）ため、単独では手法の証拠になりません。

Brier score

Brier スコア

確率予想の二乗誤差の平均。低いほど良く、無情報予想（常に p = 0.5）の値は 0.25。0.25 を安定して下回れば確率がコイン投げより情報を持ち、上回れば無情報以下（確率の付け方が逆か、自信過剰）です。

Calibration

較正

「70%と言った予想は本当に70%当たるか」。確率をビンに分け、平均予想確率と実際の上昇頻度を並べます。高確率側で実際の頻度が下回れば自信過剰。件数の少ないビンは偶然で大きく振れます。

レンジ的中率は指標として弱い 予想レンジは中心 ± 1 ATR（14日）という設計です。ATR は日々の値幅の平均なので、 レンジ幅はもともと1日の変動をおおむね覆う広さになります。したがって レンジ的中率は設計上7割前後は出るのが普通で、高くても手法の優位性の証拠にはなりません。 見るべきは「レンジが広すぎ／狭すぎではないか」であり、予想リターンの MAE と併せて判断します。

この日は広く下げた相場で、31銘柄のうち実績が上昇したのは10、下落が21、平均は −0.86% でした。 一方モデルは31銘柄中21銘柄を上昇と予想しており、平均の上昇確率は 0.60。 トレンド追随2項（合計の重み 0.80）が上向きの地合いを引き継いだ結果の上方バイアスです。 しかも高確信の予想ほどまとまって外れました——上昇確率 0.60 以上のビン（19件）は、 平均予想確率 0.70 に対して実際の上昇頻度が 0.42 で、この日は明確な自信過剰でした。 下落予想が 6/7 当たったのは、地合いが下だったこの日にたまたま向きが合っただけと見るべきです。

これは弁護の余地なくモデルの弱点の観察です。ただし1日ぶんの観察から「上方バイアスがあるから重みを下げる」と結論するのも同じ誤りで、 重みを動かすのは台帳が積み上がってからです。現時点で言えるのは「そういう外れ方をした日があった」という事実だけです。

数値の出所 上記は台帳の採点結果を overnight_forecast.py calibration と同じ定義で集計した値で、 2026-07-24 の確定終値で再採点しています（場中の暫定値で採点した速報とは小数点以下がずれます）。 台帳は営業日ごとに積み上がるため、この数字は最新の集計コマンドの出力と一致しないことがあります。 最新値は手元で python3 analysis/overnight_forecast.py calibration を実行して確認してください。
Automation

自動運用

台帳は自動で回して初めて貯まります。東証の大引け後（当日終値が確定する 15:30 以降）に run を平日ぶん回すのが素直な構成です。当日終値を asof に予想を作り、翌営業日に前日ぶんを採点します。 

# crontab: 平日 16:30 JST に「前回の答え合わせ → 翌営業日の予想」
CRON_TZ=Asia/Tokyo
30 16 * * 1-5 cd /path/to/stock_hacker && python3 analysis/overnight_forecast.py run >> ~/forecast.log 2>&1

# 較正の確認は週次で十分
0 8 * * 6 cd /path/to/stock_hacker && python3 analysis/overnight_forecast.py calibration >> ~/forecast.log 2>&1

機械可読な契約

各サブコマンドは stdout の最終行に RESULT 行を出します。通知の振り分けはこれと exit code で行います。

サブコマンドRESULT 行
forecastRESULT forecasts=<件数> universe=<成功>/<総数> data=<real|synthetic|unavailable>
gradeRESULT graded=<採点数> pending=<残保留数> data=<real|synthetic|unavailable>
runRESULT graded=<g> forecasts=<f> universe=<成功>/<総数> data=<...>
calibrationRESULT graded=<採点済み総数> data=real
exit code意味
0正常終了（data=real または data=synthetic）
2実データ全滅（data=unavailable）。予想・採点・レポートは生成されず、stderr に対処が出る
1その他のエラー（ユニバース CSV の不正など。RESULT 行なし）

grade の graded=0 は「翌営業日の実データがまだ揃っていない」＝正常（保留のまま）でも起こります。 監視は pending の残数が減り続けているかで見ます。通知の原則は 「外れが偏ったとき・データ取得不可・pending が減らないときに出す」で、 「毎日予想を出した」こと自体は台帳とレポートに残るため無条件通知はノイズです。

禁止事項 実データが取れないときに --synthetic で代替して、予想や答え合わせを「本物の市況」のように見せることは禁止です。 取得不可なら data=unavailable / exit 2 を出して静かに終了するのが正しい挙動です。 合成データは手法デモ専用で、台帳では data=synthetic と隔離され、実データの成績には混ざりません。

cron / Routine のセットアップ、通知ラッパーの例、リモート環境でのネットワーク到達性の扱いは docs/overnight-forecast.md に詳しくあります。 CLI のオプション一覧は CLI リファレンス、 Claude Code から起動する場合は /overnight スキルを参照してください。

Limitations

限界

この仕組みができないことを、できることと同じ精度で書いておきます。

Model

洗練されたモデルではない

3つのテクニカル指標を固定重みで足しただけのベースラインです。市場のマイクロストラクチャも、板情報も、需給も、ニュースも、決算も見ていません。「まず測れる基準点を置く」以上の主張はしていません。

Horizon

1日先の方向予測は本質的に難しい

翌営業日のリターンはノイズが支配的で、シグナル対ノイズ比が極めて低い領域です。的中率がコイン投げから安定して離れること自体が難題であり、離れない結果も十分あり得ます。

Sample size

少数標本では何も言えない

現在の記録は1営業日ぶんです。数十件の的中率や Brier から手法の優劣を語ることはできません。台帳が積み上がるまで、良い数字も悪い数字も保留します。

Bias

トレンド追随由来の上方バイアス

重みの 0.80 がトレンドとモメンタムなので、上昇局面のあとは上昇方向に偏りやすい構造です。実際、直近の採点日は31銘柄中21を上昇と出し、下げ相場でまとまって外しました。

Cost

取引コストを考慮していない

予想は方向・確率・レンジの当てっこであり、売買のシミュレーションではありません。手数料・スプレッド・スリッページ・約定価格（終値で建てられるとは限らない）はいずれも織り込んでいません。

Data

データ品質に依存する

既定のデータソースは yfinance（非公式 API）で、日本株では分割・配当調整の不備が起こりえます。調整の誤りは実績リターンを歪め、答え合わせそのものを誤らせます。異常な騰落を見たらまずデータを疑ってください。

最後に ここに出る予想・確率・的中率は、将来の騰落の断定でも投資助言でもありません。 機械的な条件合成の出力と、その事後測定の記録です。 たとえ将来の台帳で的中率が無情報基準を上回ったとしても、市場環境が変われば過去の成績は将来を保証しません。

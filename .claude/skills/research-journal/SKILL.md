# リサーチジャーナルへの記録

引数（対象銘柄と仮説の内容）: $ARGUMENTS

分析・仮説を「やりっぱなし」にせず、**後から機械的に当たり外れを検証できる形**で
`journal/<YYYY>/` に記録する。書式・設計思想の正は `journal/README.md`。

## いつ書くか

1. **分析の直後** — /analyze・/screen・/backtest・/earnings 等で検証可能な仮説
   （「この銘柄は〜だから60日でベンチマークに勝つ」）が得られたとき。
   レポートを作って終わりにせず、仮説として登録する。
2. **売買判断の記録** — ユーザーが売買を判断した理由を残したいとき。
   ただし記録するのは**判断の根拠となった仮説**であり、株数・約定価格などの
   個人の売買記録は書かない（それは gitignore 対象の `data/` の領分）。
3. **気づき・違和感** — 「このセクターだけ出来高が偏っている」のような観察も、
   方向（up/down/neutral）と期日を付ければ検証可能な仮説になる。

## 手順

### 1. 仮説を検証可能な形に落とす

記録前に以下を確認する。曖昧なら**ユーザーに1回だけ確認**する:

- 対象銘柄（4桁コード、複数可）
- 方向: up / down / neutral（銘柄ごとに違うなら `7203:up,6758:down` 形式）。
  direction は「同期間の ^N225 に対する超過リターン」の向きである点をユーザーと共有する
  （地合いで上がっただけでは hit にならない）
- 検証期日: 仮説の性質に合わせる（決算イベント → 決算後1〜2週間、テクニカル → 30〜60日、
  中期ファンダ → 90日以上）。既定は60日

### 2. 雛形の生成（終値スナップショット）

```bash
python3 analysis/research_journal.py new --codes 7203 --title "決算後の上方修正期待" \
    --direction up --review-days 60
```

- 記録時点の終値と ^N225 が frontmatter に自動スナップショットされ、パスが stdout に出る。
- yfinance への接続に失敗したら `--synthetic` を付けて再実行できるが、
  **合成データのスナップショットでは実データの検証にならない**。その旨がエントリに
  自動注記されるので、ユーザーに「ネットワーク回復後に作り直すべき」と伝える。
- タイトルが日本語のみだとファイル名スラッグが銘柄コードになる。分かりやすくしたければ
  `--slug earnings-upgrade` のように英語スラッグを明示する。

### 3. 本文3節の記入（Edit で追記）

生成されたファイルのプレースホルダーを実内容に置き換える:

- **## 仮説** — 何がどうなると考えるか。「〜なら hit」と機械判定に落ちる表現で書く。
- **## 根拠** — 根拠にした分析レポート（`reports/` のパス）・ナレッジ文書・データを引用する。
- **## 反証条件** — **必ず書かせる（空のまま完了にしない）**。何が起きたらこの仮説を
  捨てるかを事前に決めることが、確証バイアス・塩漬け化への最も実効的な対策
  （`knowledge/strategies/behavioral-finance-japan.md`）。価格条件（「25日線を5%割れ」）や
  イベント条件（「下方修正が出たら」）のように観測可能な形で書く。
  ユーザーが反証条件を出せない場合は「どうなったらこの見立ては間違いだったと認める？」と
  問い直して引き出す。

`## 検証結果` はプレースホルダーのまま残す（verify コマンドが追記する領域）。

### 4. 完了報告

エントリのパス・検証予定日を伝え、「期日が来たら `/journal-review` で検証する」ことを案内する。

## 注意事項

- journal/ は git 管理対象。**個人の売買記録・保有株数・金額は書かない**。
- 仮説の記録は投資助言ではない。エントリにも断定的な将来予測ではなく検証対象の仮説として書く。
- 対応コマンド: `/journal`（このスキルの薄いラッパー）。検証・振り返りは `/journal-review`
  （journal-review スキル）が担当。

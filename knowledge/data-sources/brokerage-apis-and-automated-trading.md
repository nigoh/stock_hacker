# 証券会社の発注APIと自動売買システム構築

個人が日本株の自動売買を行うための発注経路——auカブコム証券のkabuステーションAPI、立花証券e支店API、インタラクティブ・ブローカーズ証券のTWS API等——を比較し、実装アーキテクチャ（シグナル→発注→約定管理→冷却装置）を整理する。見せ玉など相場操縦とみなされ得る発注パターンの回避、レイテンシの現実と個人が戦える土俵の見極めも扱う。データ取得APIはdata-apis-and-toolsを参照。

## 前提：米国と異なる「発注API不毛地帯」の歴史

米国ではInteractive BrokersのTWS APIやAlpacaなど個人向け発注APIが早くから整備されたが、日本の大手ネット証券（SBI・楽天・松井・マネックス）は長らく公式の発注APIを提供してこなかった。背景には、システムトレード需要の小ささへの認識、誤発注リスクへの警戒、そしてサポートコストがある。転機は2019年のauカブコム証券によるkabuステーションAPI公開で、2025年時点でも個人が正規に使える国内発注APIは事実上数社に限られる。

| 経路 | 提供元 | 方式 | 特徴・制約（2025年時点） |
|---|---|---|---|
| kabuステーションAPI | auカブコム証券 | ローカルREST + WebSocket PUSH | Windows上でkabuステーション起動が必須。現物・信用・先物OPに対応。銘柄登録数やAPIコール頻度に上限あり |
| e支店API | 立花証券 | HTTP（サーバ直接） | ローカルアプリ不要でLinux/クラウドから直接叩ける数少ない経路。現物・信用対応。ドキュメントは簡素 |
| TWS API / Client Portal API | IB証券（日本法人） | ソケット/REST | 東証銘柄の発注可。API仕様は世界共通で情報が豊富。手数料体系・口座条件は国内勢と異なる |
| マーケットスピードII RSS | 楽天証券 | Excel関数（RSS） | 正式なAPIではなくExcel経由の準自動化。VBAと組み合わせた発注が可能だが堅牢性は低い |
| 各社の非公式スクレイピング | — | — | 規約違反となる場合が多く、口座凍結リスク。ログイン仕様変更で即死するため推奨されない |

## 主要APIの機能比較

**kabuステーションAPI（auカブコム証券）**は、ローカルPCで動くkabuステーションが取引所側との通信を仲介し、ユーザーのプログラムは `localhost` のRESTエンドポイントを叩く構成である。トークン認証（APIパスワード→ワンタイムトークン）を経て、注文発注・訂正・取消、残高・注文照会、板情報（時価情報スナップショット）取得ができ、登録銘柄の時価はWebSocketでPUSH配信される。制約として、(1) Windows実機または仮想マシンの常時稼働が必要、(2) 時価PUSH対象の銘柄登録数に上限（数十銘柄規模）、(3) APIコールにレート制限があり大量銘柄の高頻度ポーリングには向かない、(4) 利用条件（対象口座の開設や取引実績による無料化条件など）が設定されている点に注意する。細かい数値仕様は改定されうるため必ず公式ドキュメントで確認する。

**立花証券e支店API**は、証券会社サーバへ直接HTTPリクエストを送る方式で、ログインでセッション（仮想URL）を取得し、注文・照会（request系）、マスタ情報、時価、約定イベント通知（event系）の各インターフェースを使う。ローカルの中継アプリが不要なため、Linuxサーバやクラウド（VPS）上で完結する自動売買を組みやすいのが最大の利点である。一方でドキュメントやサンプルは大手に比べ簡素で、利用者コミュニティも小さいため、仕様解釈を自力で検証する覚悟が要る。

**IB証券**は日本居住者も口座開設でき、TWS APIで東証銘柄を発注できる。Pythonライブラリ（ib_insync等のコミュニティ実装を含む）や書籍・情報が世界的に豊富な点が強みだが、国内固有の注文条件（引成・不成等の細かい執行条件）や税務処理（特定口座の扱い）は国内証券と異なる場合があるため確認が必要である。

## 自動売買システムの実装アーキテクチャ

実運用に耐えるシステムは、およそ次のパイプラインと状態管理で構成される。

1. **データ取得層**：時価・板のPUSH受信またはポーリング。タイムスタンプを付けて生データをログに残す（後の検証・デバッグの生命線）。
2. **シグナル層**：戦略ロジック。データ層・発注層から分離し、バックテストと同一コードを使えるようにする（実装乖離バグの防止）。
3. **リスクチェック層（プリトレードチェック）**：発注前に「1注文の金額上限」「銘柄あたり・口座全体のポジション上限」「値幅制限・呼値の妥当性」「同一注文の重複（冪等性キー）」を機械的に検査する。誤発注の大半はここで止められる。
4. **発注・約定管理層**：注文を状態機械として管理する——`未発注 → 発注中 → 受付済 → 一部約定 → 全約定/取消/失効`。API応答のタイムアウト時は「発注されたか不明」という中間状態が必ず生じるため、注文IDで照会して状態を確定させてから再送する（盲目的リトライは二重発注の典型原因）。
5. **レコンシリエーション**：起動時と定期的に、システム内部のポジション・注文簿を証券会社側の照会結果と突合し、齟齬があれば新規発注を停止する。
6. **冷却装置（kill switch）**：日次損失額、連続エラー回数、単位時間あたり発注数、想定外の約定価格乖離などが閾値を超えたら全注文取消＋新規停止に落とす回路を、戦略ロジックとは独立に実装する。2005年のジェイコム株誤発注事件（みずほ証券）が示すように、発注系の暴走は分単位で致命傷になる。

レイテンシがもたらすコストは直感的には次のように見積もれる。シグナル発生から約定までの遅延を $\Delta t$、銘柄のボラティリティを $\sigma$（単位時間あたり）とすると、その間の価格変動の標準偏差は拡散のスケーリングにより

$$E[|\text{価格ずれ}|] \sim \sigma \sqrt{\Delta t}$$

に比例する。遅延が4倍になってもずれは2倍にしかならない一方、$\sigma$ が大きい銘柄・時間帯（寄付き直後など）では同じ遅延でもコストが跳ね上がる。つまり個人が最適化すべきは絶対的な速さよりも「遅延に対して頑健な戦略の選択」である。

## 相場操縦とみなされ得る発注パターンの回避

自動売買では、悪意がなくてもアルゴリズムの挙動が金融商品取引法第159条の相場操縦（変動操作・仮装売買・馴合売買）に該当し得る点に最大限注意する。証券取引等監視委員会は個人による**見せ玉**（約定させる意図のない大量注文で板を厚く見せ、反対側で約定後に取り消す行為）を実際に摘発しており、課徴金事例も多数ある（2025年時点）。自動売買設計上の具体的な注意点は以下の通り。

- **高い注文取消率**：発注→即取消を高頻度で繰り返すロジック（例：板の反応を探るping注文）は、意図にかかわらず見せ玉と評価されるリスクがある。取消率・板滞在時間をモニタリングする。
- **自己対当（仮装売買）**：同一人物の買い注文と売り注文が対当して約定すると仮装売買に該当し得る。複数戦略を同一口座で走らせる場合、社内クロスを防ぐ機構（同一銘柄の反対注文の同時存在チェック）が必須。
- **終値・寄付き関与**：引け間際の価格形成に影響する連続発注は終値関与とみなされ得る。
- 証券会社側も売買審査システムで異常な発注パターンを検知しており、警告や口座利用制限の対象になる。

なお2018年の金商法改正で導入された**高速取引行為者（HFT業者）登録制度**（2025年時点）は、コロケーション利用等により取引所システムとの応答時間を短縮して自動発注する者を登録制とするものである。証券会社の個人向けAPIをインターネット経由で使う通常の個人は要件に該当しないのが一般的だが、制度の存在自体が「速度競争の土俵は登録業者のもの」という線引きを示している。

## 個人が戦える土俵の見極め

東証arrowheadの注文応答はマイクロ秒〜ミリ秒オーダーで、コロケーションに置かれたHFT業者のレイテンシと、個人がインターネット＋証券会社API経由で実現できる数十〜数百ミリ秒との差は3〜5桁ある。したがって板の裁定・最良気配の奪い合いといった速度勝負は構造的に不可能である。個人の自動売買が意味を持つのは、(1) 日次〜分足レベルのシステムトレード（速度でなく仮説の質で勝負）、(2) 寄付き・引けの単一約定を狙う戦略（レイテンシがほぼ無関係）、(3) 決算・開示イベント後の数分〜数日の反応を捉えるイベントドリブン、(4) 裁量トレードの執行部分だけを自動化する半自動運用、といった領域である。自動化の最大の便益は速度ではなく、規律の強制（感情の排除）と検証可能性（全発注のログ化）にあると理解しておくのが実務的である。

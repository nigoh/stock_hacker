# XBRLの活用とスクレイピングの法務・倫理

決算短信サマリーと有価証券報告書のXBRLは日本株の財務データを機械可読で得る正規ルートだが、コンテキスト・単位・拡張タクソノミの扱いを誤ると静かに壊れた数値が出る。
本稿は前半でXBRLの構造と解析実務・落とし穴を、後半でWebスクレイピングをめぐる法的論点（著作権法30条の4、利用規約、不正競争防止法、サーバ負荷）と実務上の作法を整理する。
**後半は法律相談ではなく論点の地図である。適法・違法の判断は事案ごとに異なり、実行前に専門家に相談すべき事柄として扱う。**

## 1. 日本株で出会う二つのXBRL

XBRL（eXtensible Business Reporting Language）は財務報告のためのXMLベースの規格で、数値に「どの勘定科目か」「いつの期間か」「どの単位か」というメタ情報を機械可読な形で付与する。日本株の実務で扱うのは主に次の二系統で、提供元も粒度も違う。

| | 決算短信サマリーXBRL | EDINET（有報・半期報告書等）XBRL |
|---|---|---|
| 提供元 | 東証（TDnet） | 金融庁（EDINET） |
| 対象 | サマリー情報・財務諸表、業績予想の修正、配当予想の修正、コーポレート・ガバナンス報告書 | 有価証券報告書、半期報告書、臨時報告書、大量保有報告書 等 |
| 粒度 | サマリー中心（主要な段階利益・EPS・通期予想） | 財務諸表本表＋注記まで詳細 |
| タイミング | 決算発表と同時（速報） | 事業年度末後3か月以内（有報） |
| 取得 | 無料の公式APIなし（有料APIまたは再配信） | **EDINET API v2**（無料、要APIキー。2025年時点） |
| 用途 | 速報値の即時取り込み | 遡及的・網羅的な財務分析 |

実務上の分担は「速報は短信サマリー、精査と遡及は EDINET」となる。本リポジトリの `stocklib/edinet.py` は EDINET API v2 の CSV 出力（`type=5`、XBRL項目を縦持ちにしたUTF-16タブ区切り）を使っており、XBRLインスタンスを直接パースせずに済ませる設計である。CSV出力で足りるならそれが最短で、以下のインスタンス解析は「CSVにない項目が要る」「タクソノミの版差を自分で管理したい」場合の手段と位置づけるとよい。

## 2. XBRLを構成する四つの軸

XBRLの数値（ファクト）は、次の四つが揃って初めて意味が確定する。どれか一つを取り違えると、桁も期間も違う数字が黙って混入する。

1. **要素名（element）**——勘定科目の識別子。`NetSales`（売上高）、`OperatingIncome`（営業利益）など。名前空間（タクソノミ）とセットで一意になる。
2. **コンテキスト（context）**——いつ・誰の数値か。期間型（Duration、損益計算書項目）と時点型（Instant、貸借対照表項目）の区別、当期／前期、連結（`ConsolidatedMember`）／個別（`NonConsolidatedMember`）、予想値（`Forecast` 系）などが `contextRef` で指定される。
3. **単位（unit）**——`unitRef` が指す通貨（JPY）や株数（shares）。金額は原則として**円単位の実数**で格納される（画面表示の「百万円」は表示上の丸め）。
4. **精度（decimals / scale）**——丸めの桁。`decimals="-6"` は百万円単位への丸めを意味する。

タクソノミは年度版で更新される。EDINET タクソノミの名前空間URIには版年月日が含まれ（例: `.../jppfs/2025-11-01/jppfs_cor`）、年度をまたぐと要素の追加・廃止が起きる。**名前空間URIをコードにハードコードすると翌年に壊れる**ので、インスタンス側の宣言から動的に解決するのが安全である。

## 3. Pythonでの解析

選択肢は大きく三つある。

- **`arelle`**（オープンソースのXBRLプロセッサ）——タクソノミの読み込み、計算リンク（合計の整合検証）、表示リンクまで扱える本格派。Python API（`arelle.Cntlr`）から呼べる。重いが、注記や連結・個別の階層を正確に辿るならこれが正道。
- **生XMLのパース**——`xml.etree.ElementTree` や `lxml` でインスタンスを直接読む。必要な要素が少数なら十分軽量。
- **EDINET の CSV 出力**——API の `type=5`。前処理済みで最も手軽（本リポジトリの既定）。

生XMLで特定要素を拾う最小例:

```python
import xml.etree.ElementTree as ET

root = ET.parse("jpcrp040300-q1r-001_E00001-000.xbrl").getroot()
ns = {"jppfs": "http://disclosure.edinet-fsa.go.jp/taxonomy/jppfs/2025-11-01/jppfs_cor"}
for el in root.findall("jppfs:NetSales", ns):
    # contextRef で期間・連結/個別・当期/前期を判別してから使う
    print(el.get("contextRef"), el.get("unitRef"), el.get("decimals"), el.text)
```

ポイントは、値（`el.text`）を取る前に必ず `contextRef` を判定することである。同じ `NetSales` が当期連結・前期連結・当期個別…と複数回現れるため、フィルタなしで最初の一件を取ると何の数字か分からないまま処理が進む。

## 4. 拡張タクソノミという壁

XBRLの「X」は eXtensible（拡張可能）であり、企業は標準タクソノミにない勘定科目を**独自要素として拡張定義できる**。これが企業間比較を最も強く阻む要因になる。

- 同じ「売上高」でも、標準要素が `NetSales`／`OperatingRevenue`／`NetSalesOfCompletedConstructionContracts`（建設業）等に分かれ、さらに企業独自の拡張要素が使われることがある。業種別の表示科目の慣行差がそのまま要素名の差になる。
- 拡張要素は名前空間が企業固有（EDINETコードを含む）になるため、横断集計のコードから見ると「未知の要素」として落ちる。**落ちたことに気づかず合計が過少になる**のが最悪のパターンである。
- IFRS採用企業は別系統のタクソノミ（`jpigp` 系）を使い、段階利益の定義自体が日本基準と異なる（[`../fundamental/reading-japanese-financials.md`](../fundamental/reading-japanese-financials.md)）。

実務的な対処の型は三段構えになる。(1) 標準要素を優先的に探し、(2) 見つからなければ業種別の代替候補・自前のマッピング辞書を当て、(3) 最後に**合計値との整合チェック**（内訳の和が本表の合計と一致するか、計算リンクを使うか）で取りこぼしを検出する。「機械的にマッピングし切れる」という前提を置かず、不一致を検出したら人手で原資料に当たる運用を組み込むのが安全側である。

## 5. 実務的な落とし穴

| 落とし穴 | 症状 | 対処 |
|---|---|---|
| **訂正報告書** | 過年度の数値が後から書き換わる。元の報告書だけ見ると古い値のまま | `docID` 単位でなく提出履歴で管理し、訂正報告書（訂正有報等）を検索して上書き。バックテストでは「当時見えていた値」と「訂正後の値」を分けて保持する |
| **連結／個別の取り違え** | 単体の小さい数字を連結として使い、規模が一桁ずれる | `contextRef` の `ConsolidatedMember` / `NonConsolidatedMember` を必ず判定。持株会社では特に致命的 |
| **期間コンテキストの誤り** | 前期の値を当期として集計、四半期累計と単四半期の混同 | Duration の開始・終了日を実際に読む。「当期」ラベルへの依存を避ける |
| **予想値の混入** | 会社予想が実績として集計される | 予想系コンテキストを明示的に除外する |
| **単位の千円／百万円** | 1000倍・100万倍のずれ | XBRLの値は原則円単位。表示資料の単位と比べる際に丸め（`decimals`）を考慮する |
| **タクソノミの版差異** | 昨年動いたコードが今年落ちる | 名前空間URIを動的解決。年度をまたぐ処理では版ごとの要素対応表を持つ |
| **少数株主持分等の科目改称** | 時系列で名前が変わり系列が切れる | 過年度の要素名変更（例: 少数株主→非支配株主）を辞書で吸収 |

これらは静かに間違う類の不具合である。**取り込んだ数値を必ず一度は原資料（PDF）と突き合わせる**検証を、パイプラインの受け入れテストとして持っておきたい。

## 6. スクレイピングをめぐる法的論点（論点整理であり法律相談ではない）

XBRLやAPIで取れない情報を「Webページから取りたい」場面は必ず来る。ここは法的にも倫理的にも単純な白黒がつかない領域で、以下は**論点の地図**であって適法性の保証ではない。個別の実行可否は、対象サイトの規約・データの性質・取得態様によって変わるため、業務で行うなら専門家に相談すべき事柄として扱う。

### 6.1 著作権法30条の4（情報解析目的の利用）

2018年（平成30年）の著作権法改正で整備され、**2019年1月1日施行**の第30条の4は、著作物を「**表現された思想又は感情を自ら享受し又は他人に享受させることを目的としない場合**」には、必要と認められる限度で利用できる旨を定めている。情報解析（多数の著作物から情報を抽出・比較・分類等する解析）はその例示に含まれ、統計解析・機械学習のためのデータ収集に道を開いた規定と一般に理解されている。

限界として押さえるべき点が二つある。

- **但し書き**——「著作権者の利益を不当に害することとなる場合は、この限りでない」。たとえば情報解析用に販売されているデータベースを、購入せずに収集して代替するような態様は、この但し書きに触れうるとの議論がある。
- **享受目的が混ざる場合**——収集した本文をそのまま再掲・再配信すれば、それは解析ではなく享受目的の利用であり、30条の4の射程外と解される余地が大きい。「解析のための取得」と「取得したものの二次配信」は別問題として切り分ける必要がある。

### 6.2 利用規約（契約）は著作権法とは別レイヤー

ここが最も誤解されやすい。**著作権法上の権利制限規定は「著作権侵害にならない」ことを述べるにとどまり、サイト利用規約に基づく契約上の義務を免除するものではない**と一般に整理されている。多くの金融情報サイト・証券会社サイトは、自動収集・再配信・複製を規約で明示的に禁じている（本ナレッジベースでも、株探の機械的取得禁止、証券口座画面の再配信禁止に触れている）。

したがって検討順序は「著作権法上どうか」だけでなく、**「その規約に同意して利用しているか」「規約が禁じていないか」**を先に確認する形になる。規約違反が直ちに違法行為になるかは別論点だが、契約解除・アカウント停止・損害賠償請求といった民事上のリスクは規約の側から生じうる。

### 6.3 不正競争防止法（限定提供データ）

2018年改正・**2019年7月1日施行**で、「**限定提供データ**」——業として特定の者に提供する情報として、電磁的方法により相当量蓄積され、かつID・パスワード等で管理されている技術上・営業上の情報——の不正取得・使用・開示が不正競争行為に位置づけられ、差止請求等の対象となった。有料の市場データ・財務データベースは、この要件を満たしうる典型例である。認証を回避して取得したデータを使う・再配布するといった態様は、この枠組みで問題になりうる。

### 6.4 サーバへの負荷と業務妨害

技術的・倫理的にも法的にも重いのがこの論点である。日本では**岡崎市立中央図書館事件（Librahack事件、2010年）**が象徴的な事例として参照される。図書館の蔵書検索システムに対して自作クローラで高頻度アクセスを行った利用者が偽計業務妨害の疑いで逮捕・勾留され、後に起訴猶予となり、最終的には図書館側が「クローラ利用に落ち度はなかった」旨を表明し、障害の原因はシステム側にあったとされた経緯を持つ。

この事例から実務が学ぶべきは、法的評価の結論そのものよりも、**「相手のシステムが耐えられない量のアクセスは、悪意がなくても業務妨害として扱われる可能性がある」**という前提である。加えて、米国では他人のサーバ資源への過度な干渉を動産不法侵入（trespass to chattels）の法理で捉える議論や、不正アクセス関連法（CFAA）の適用範囲をめぐる訴訟（hiQ v. LinkedIn 等）が積み重ねられてきた。日本法にそのまま対応する法理があるわけではないが、「公開されている＝いくらでも自動取得してよい」という単純な理解が国際的にも支持されていないことは押さえておきたい。

なお、取得対象に個人情報が含まれる場合は個人情報保護法の論点が別途生じる。企業の開示情報を扱う限りでは正面から問題になりにくいが、掲示板・SNSの投稿者情報などを扱うなら考慮が要る。

### 6.5 実務上の作法

法的評価とは別に、技術者の作法として広く共有されている最低限は次の通り。守っても適法性が保証されるわけではないが、守らない理由は基本的にない。

- **robots.txt を尊重する**——法的拘束力の有無は議論があるが、サイト運営者の意思表示として扱う。
- **レート制限**——同時接続を1に絞り、リクエスト間に十分な間隔（秒単位）を置く。相手のサービス時間帯・繁忙時間を避ける。
- **User-Agent を明示する**——ブラウザを詐称せず、目的と連絡先（URLやメールアドレス）を書く。問題があれば連絡してもらえる状態を作る。
- **キャッシュして再取得を減らす**——一度取ったものは保存し、差分だけ取りに行く。開発中の試行錯誤で同じページを何度も叩かない。
- **取得目的と範囲を最小化する**——全ページを機械的に舐めるのではなく、必要な範囲だけを取る。
- **再配信しない**——取得物をそのまま公開・共有しない。これは規約・著作権の両面でリスクが最も高い行為である。

## 7. 結論：公式APIを優先する

日本株に関しては、スクレイピングを選ぶ必然性がそもそも薄い。

- **財務・法定開示**——EDINET API v2 が無料で XBRL・CSV を提供する（要APIキー、2025年時点）。有報・半期報告書・大量保有報告書まで機械可読で取れる。
- **株価・銘柄マスタ・信用残・投資部門別など**——J-Quants API（JPX総研）が公式ルートとして存在する。無料プランは12週間遅延だが、過去データの機械処理には十分（2026年時点）。
- **マクロ統計**——e-Stat API、日銀の時系列統計データ。

公式APIを使えば、規約上の位置づけが明確で、データ形式が安定し、仕様変更が告知され、相手のサーバに想定外の負荷をかけない。スクレイピングはこの三つをすべて失う代わりに、APIにない情報を得る手段である。**「APIで取れないか」を先に確認し、取れないと分かってから初めて、規約・負荷・目的を検討する**——この順序を崩さないことが、技術的にも法務的にも一番割の合う運用になる。取得手段の全体像は [`market-data-apis-catalog.md`](market-data-apis-catalog.md) を参照。
